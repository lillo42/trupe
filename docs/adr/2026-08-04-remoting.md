# ADR 2026-08-04: Remoting — TCP Transport with JSON Serialization

- **Status**: Proposed
- **Date**: 2026-08-04
- **Deciders**: @lillo42
- **Scope**: Remoting only. Clustering (membership, discovery, placement) is intentionally out of scope and will be addressed by a follow-up ADR.

## Context

Trupe is currently a single-process actor model framework for .NET. `IActorReference`, mailboxes, supervision, and the actor registry all operate in-memory within one `ActorSystem`. To enable distributed scenarios, actors on one node must be able to send messages to actors on another node — i.e. **remoting** — before any cluster coordination is built on top of it.

Requirements and constraints that shape this decision:

1. **AOT compatibility** — Trupe is Native AOT compatible; remoting must not break this. Any serialization must work with source-generated `System.Text.Json` contexts (no runtime reflection).
2. **Existing abstractions must keep working** — `Tell`, `TellAsync`, and `AskAsync` semantics should be preserved across the wire; a remote `IActorReference` should feel identical to a local one.
3. **Minimal dependencies** — the project is a lightweight, learning-oriented framework; we avoid heavy stacks (no gRPC, no Orleans) for the first remoting iteration.
4. **Clustering comes later** — the remoting layer must not hard-code single-node assumptions that would block future membership/placement, but it must not implement them now either.

## Decision

We will introduce a new package, **`Trupe.Remoting`**, providing node-to-node messaging built on:

1. **Transport: raw TCP sockets.**
   - Length-prefixed framing: each message on the wire is a 4-byte little-endian length header followed by a JSON payload.
   - One long-lived TCP connection per (local node, remote node) pair, with automatic reconnect and message buffering during reconnection.
   - TLS is deferred; the first iteration targets trusted networks. The transport is hidden behind an interface so TLS or another transport can be added later.

2. **Serialization: JSON via `System.Text.Json`.**
   - Message payloads are serialized with source-generated `JsonSerializerContext` to remain Native AOT compatible.
   - Message type is carried as a string discriminator (`"Type": "MyNamespace.Greet, MyAssembly"`-style name) in the envelope, resolved against a user-registered message registry — no `Type.GetType` reflection at runtime.

3. **Wire envelope.** Every message is wrapped in a versioned envelope:

   ```json
   {
     "version": 1,
     "type": "Example.Greet",
     "correlationId": "01J…",   // null for Tell
     "target": "actor/greeter",  // logical actor address
     "payload": { "name": "World" }
   }
   ```

   - `correlationId` links `Ask` requests to responses; the remote node replies with the same correlation id.
   - `target` is a logical actor address (`actor/{id}`) resolved through a remote-aware `IActorRegister` lookup on the receiving node.

4. **Remote actor references.**
   - A `RemoteActorReference` implements `IActorReference`; `Tell`/`TellAsync` serialize and enqueue onto the connection, `AskAsync` registers a pending request keyed by `correlationId` with a timeout.
   - Local code is unchanged: obtaining a remote reference returns the same interface.

5. **Explicit addressing, no auto-discovery (yet).**
   - Nodes are configured with a listen endpoint (`host:port`) and a static list of known peers. This is deliberately crude; the clustering ADR will replace static peer lists with membership and introduce placement/routing.

## Consequences

### Positive

- Remoting stays AOT-compatible: TCP sockets and source-generated JSON have no reflection requirement.
- Zero new third-party dependencies beyond the BCL (`System.Net.Sockets`, `System.Text.Json`).
- Small, understandable surface — appropriate for a learning-oriented framework.
- Envelope versioning and the transport interface leave room for TLS, compression, or a different transport later.

### Negative / trade-offs

- JSON is less compact and slower than binary formats (protobuf, MemoryPack). Accepted for v1: simplicity and debuggability win; the envelope design allows adding a binary codec later.
- No built-in security: no TLS, no authentication. Remoting must only be used on trusted networks until a follow-up hardening ADR.
- Static peer configuration means no resilience to topology changes — explicitly deferred to the clustering ADR.
- `Ask` across nodes introduces latency and timeout semantics that local `Ask` does not have; these must be documented.

## Alternatives Considered

| Alternative | Rejected because |
|-------------|------------------|
| **gRPC / HTTP-2** | Heavy dependency, generated-code tooling, and streaming semantics we don't need yet; overkill for v1 remoting. |
| **Protobuf / binary serialization** | Better performance, but adds schema/tooling complexity and hurts debuggability; JSON keeps v1 simple and AOT-safe via source generation. |
| **Microsoft Orleans** | Pulls in an entire distributed runtime; contrary to Trupe's lightweight, learning-oriented goals. |
| **Named pipes / IPC only** | Solves local-machine scenarios but not true network remoting. |
| **Wait and build clustering first** | Remoting is the prerequisite; building both at once makes the design unreviewable. Remoting lands first, clustering follows. |

## Open Questions

- Reconnect backoff policy (exponential with jitter — defaults to be decided during implementation).
- Maximum message size guard (proposal: 1 MB default, configurable).
- Whether `Context.Response` flows back through the envelope unchanged for `Ask`, or needs a dedicated response envelope type.
- Heartbeat/keep-alive strategy for idle connections (likely TCP keep-alive initially; app-level ping deferred to clustering).
